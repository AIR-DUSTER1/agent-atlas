# Operator Runbook

> 目标：让值班人员在不猜测架构的前提下完成隔离、恢复、验证和记录。
> 所有命令默认使用 `production.env` 与 `docker-compose.production.yml`。

## 1. 磁盘水位高

1. 确认数据卷占用：`docker system df`、宿主 `df -h` / PowerShell 磁盘统计。
2. 把最新备份复制到异机，验证 manifest。
3. 查看审计归档、容器日志和备份保留策略。
4. 不删除 `web-config.json`、journal、checkpoint、memory 或当前备份。
5. 恢复空间后重启，运行 `data:check`，补一份新基线备份。
6. 记录：触发时间、水位、删除对象、备份名、恢复结果。

## 2. 配置损坏 / 解密失败

1. 记录 `startup_check_failed` / `config_secret_decrypt_failed` 日志。
2. 停止服务，保留原 `/data` 不覆盖。
3. 检查 `DATA_KEY` 是否变化；从密钥系统恢复正确值。
4. 若 Key 无法恢复，使用匹配旧的未加密备份或重新初始化配置。
5. 恢复后验证登录、供应商、模型与旧会话。
6. 不得用新 `DATA_KEY` 直接覆盖仍含旧密文的配置。

## 3. Journal 坏行

1. 运行 `data:check`，确认坏行数量与 schemaVersion。
2. 启动时会自动隔离到 `.corrupt`；保留隔离文件用于取证。
3. schema 过新：回滚镜像，不要继续写。
4. 数据损坏影响会话：停止服务，恢复最近通过校验的备份。
5. 重启后检查旧会话 transcript，创建新备份。

## 4. 外部模型不可用

1. 查看 `/api/diagnostics`、模型错误与熔断指标。
2. 核对供应商 URL、Key、模型名和协议。
3. 若上游故障，切换到配置好的 fallback。
4. 不要在未确认幂等性时手动重放大量请求。
5. 记录供应商故障窗口、错误率、切换时间与用户影响。

## 5. MCP 进程异常 / 泄漏

1. 确认问题只影响某个 server，不要先重启整个宿主。
2. 查看 MCP 状态、stderr 和容器进程树。
3. 终止异常 server 后重新连接；生产单实例最稳妥方式是重启 Agent 容器。
4. 验证其他 MCP server、内置工具和审批仍可用。
5. 保留命令、版本、退出码和日志片段。

## 6. 端口占用

1. `docker compose ps` 确认是否已有实例。
2. 查 Host 端口绑定与运行进程。
3. 不要启动第二个写同一数据卷的实例。
4. 释放旧实例或更换 `AGENT_PORT`，再验证 `/healthz`。
5. 记录占用进程和变更端口。

## 7. 认证失败风暴

1. 观察 429、401、`agent_http_requests_total` 和代理访问日志。
2. 确认不是代理层错误覆盖来源 IP。
3. 保留 `METRICS_TOKEN` 与用户登录路径分离。
4. 在代理层对异常来源限流/封禁；不要关闭认证或缩短失败窗口。
5. 若误封合法用户，等待冷却并排查密码/客户端配置。

## 8. 备份失败

1. 查看命令退出码与 `data:check`。
2. 检查磁盘、权限、manifest、时间、文件名与 SHA-256。
3. 若备份目录不完整，不要向恢复流程提供该备份。
4. 修复空间/权限后重新备份；必要时直接从已知良好异机副本恢复。
5. 记录失败原因与下一次成功备份。

## 9. SSE 断连 / 页面卡住

1. 看 `/healthz`、`readyz` 和反向代理缓冲配置。
2. 浏览器 Network 检查 SSE 是否 200、是否被代理攒包。
3. 检查服务端日志的 `agent_sse_disconnects_total` 与流状态。
4. 刷新页面从 transcript 恢复；不重复提交同一条用户消息。
5. 若静态模块 404，重新发布前端产物并重启旧服务进程。

## 10. 事件结束记录

每次事故至少记录：

- 开始/结束时间与影响范围；
- 版本、镜像 digest、配置变更；
- 触发的告警与关键 requestId；
- 执行的命令与结果；
- 恢复的备份名 / 数据校验；
- 根因、短期修复、长期预防项。
