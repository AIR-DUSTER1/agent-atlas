# 评测基线与能力缺口分析

> 评测日期：2026-11-19
> 被测版本：agentatlas 0.9.0-beta.17（commit `19f7266`）
> 评测平台：agent-bench（本地 `agent_bench.db`）
> 本文是可公开的评测结论；复现步骤、内部归因和优化计划见仓库内 `.plans/`。

---

## 1. 结论摘要

在**同一 Judge、同一评测集、同一模型**（opencode 网关 / `deepseek-v4.1-flash`）下，
把 agentatlas 走完整 SSE 链路（LangGraph 多节点 + 工具装配 + 审批）与「裸模型直连网关」
做了对照：

| 评测集 | agentatlas（完整链路） | 裸模型（无编排） | 差异 |
|---|---|---|---|
| Prompt 推理（12 题） | **4.77**（12/12 通过） | 4.96 | −0.19 |
| RAG 知识库（12 题） | **3.05**（1/12 通过） | 4.14（8/12） | **−1.09** |
| Tool 工具调用（10 题） | **2.81**（1/10 通过） | 3.77（2/10） | **−0.96** |

**核心结论：在当前评测集上，agentatlas 的编排层没有带来增益，反而在 Agent 场景显著减分。**
根因不在模型，而在「提示词鼓励用工具 + 依赖环境未配置」的组合会让 Agent 过度探索，
并产出无依据的自我辩解，被 Judge 判为幻觉。

## 3. 关键度量：过度探索

Tool 集第 1 题（「查询数据库：销量最高的产品」）的轨迹对比：

| 指标 | agentatlas | 裸模型 |
|---|---|---|
| 工具调用次数 | **32** | 0 |
| 耗时 | **325.9 秒** | 6.4 秒 |
| 输入 token | **502,746** | — |
| 准确性 | 1.0 | 2.0 |

agentatlas 依次尝试 `list_dir` → `grep_search` → `read_file` → `terminal`，
在项目里反复搜索数据库与销售数据，最终输出一段「我做了什么（以下都是只读查询）」的核查清单。

RAG 集的同类现象（12 题中 9 题触发）：

```
retrieve_docs  → 返回「未配置外部 RAG 服务」
     ↓ 退化为
grep_search / list_dir  → 搜本地项目，无结果
     ↓ 输出
「我查了一圈没找到，这是我的核查清单」
```

平均单题耗时 170 秒（最长 364 秒），而裸模型 8–26 秒。

## 4. 三层根因

### 4.1 评测集与能力不匹配（外部因素）

Tool 集期望工具分布：

| 期望工具 | 题数 | agentatlas 是否具备 |
|---|---|---|
| `sql_query` | 7 | ❌ 不存在 |
| `knowledge_search` | 1 | ❌ 不存在（近似能力为 `retrieve_docs`） |
| `calculator` | 1 | ✅ 存在 |
| 空（拒答题） | 1 | — |

**9/10 题的期望工具在代码库中不存在。** 这类题无论怎么调优都无法通过，
属于评测集与产品能力边界不匹配，不应作为 Agent 质量指标。

RAG 集则存在协议缺口：每题 `reference_context` 含标准答案，但该字段只提供给 Judge，
**从未注入被测 Agent**，也没有把文档预灌入知识库。因此测的是「模型面对空知识库的表现」，
而不是「RAG 链路质量」。

### 4.2 空依赖下强制探索（产品缺陷）

提示词明确要求「需要事实依据时优先用工具而不是凭记忆编造」。
当工具返回「未配置 / 不可用」时，Agent 没有止损策略，继续换工具重试，
并把无效尝试写进回答当作尽职证明 —— Judge 判为无依据陈述。

### 4.3 工具可用性声明不准确（产品缺陷）

Prompt 集第 12 题（水池注水）：回答称「已调用计算器验证」，
但轨迹中 `calculator` 返回 `null`（未真正执行）。提示词鼓励用工具，
模型就把「打算调用」写成了「已经调用」。

## 5. 能力改进方向

按性价比排序：

| 优先级 | 改进项 | 预期影响 |
|---|---|---|
| P0 | 提示词增加「工具不可用即止损」硬规则；禁止罗列无效核查过程；禁止声称未实际发生的工具调用 | 直接针对幻觉 2.30 / 2.75，改动小 |
| P1 | 新增 `sql_query` 类结构化查询能力（接外部数据库 + 审批登记） | 覆盖 Tool 集 7/10 题，也是真实产品缺口 |
| P2 | 精简常驻工具（24 个中 4 个为演示项），按场景分组装配 | 降低选择噪声与 schema 开销 |
| P3 | RAG 评测协议修正：预灌知识库后再测，或标注为环境缺口 | 让 RAG 分数反映真实链路质量 |

## 7. 重要说明：关于此前一版对比报告

此前的《ZCode 与 agent-atlas 评测对比报告》中，
标注为「agent-atlas」的三个分数（4.95 / 4.25 / 3.96）实际来自
`agent_version id=10` —— 该版本指向 **`opencode-deepseek-v4.1-flash`（type=prompt）**，
即裸模型直连网关，不经过 agentatlas 的任何编排。

判定依据：

- `agent_version 10` 的 config 仅含 `base_url` / `api_key` / `model` / `temperature`；
- 真正的 agentatlas 是 `agent` 表 id=6（`type=external_http`），其版本为 av 6–9；
- 该三套运行（run 34/35/36）的 `intermediate` 字段每题只有一条 `llm_call`，
  零工具调用 —— 真实 agentatlas 在 Tool 集会产生大量工具轨迹。

因此那三个分数应理解为**模型基线**，而非平台能力。
本文件第 1 节的对照表已按真实口径重新测量。
